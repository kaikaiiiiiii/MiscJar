## 1. 目标

在常规压缩包之外，提供另一种打包方案，并满足：

1. **看起来是 A 打包（zip），实际上是 B 打包（自研容器）**
2. **让自动化处理流程识别为 A 打包**（走压缩包的正常通道，而不是被当成可疑的未知格式）
3. **能解出一些内容**，以掩盖剩余的所有内容
4. 真实内容可完整还原，且容器本身可多批次共存、可扩展

**不是**目标：防止别人读到内容。保密需要真正的加密，与本方案无关。

## 2. 核心机制

自动化流程（网盘扫描、批处理脚本）拿到一个 `.zip` 后会尝试解压。我们的产物**是一个 SQLite 数据库**，不含任何 zip 结构；它的内部有一个 **gzip 流**——而 gzip 容器的魔数 `1f 8b 08` 固定在流开头。

于是产生了两条性质：

| | |
|---|---|
| **扫描型解压工具**（WinRAR、7-Zip） | 扫文件头找已知格式 → 命中**偏移最低**的 gzip 流 → **解出提示文件** |
| **严格格式解析器**（Python `zipfile`、libarchive、.NET） | 找不到 EOCD / 中央目录 → **判为非法文件** |

**关键在于让提示文件成为文件中偏移最低的那一个 gzip 流。** 靠两点保证：

1. **提示文件独占 page 2**（偏移 < 2×pageSize），而载荷在 page 3+（偏移 ≥ 2×pageSize）→ 载荷字节**结构上**不可能更低
2. 扫描器从文件头**正向**扫魔数，取第一个命中 → 必然是提示文件

> 注意：载荷是压缩后的字节，**可能随机撞上 gzip 魔数**（25MB 载荷约 72% 概率至少一次）。这些命中都在提示文件**之后**，扫描器扫不到它们，无害。但也因此**不能**把验证写成"全文件恰好一处 gzip 魔数"——那会误杀合法归档。当前判据见 3.5（提示文件落在 page 2 内）。

## 3. 关键决策

### 3.1 提示文件：gzip，不是 zip

| 方案 | 结论 |
|---|---|
| **gzip** ✅ | 单向流 + 固定魔数。扫描器"从头正向扫魔数，取偏移最低者"，规则统一、可预测。WinRAR 与 7-Zip 都支持。 |
| zip ❌ | 随机访问格式。EOCD 在尾部、中央目录记录绝对偏移，嵌入后偏移全部失效；不同实现的补偿与选取规则相反（扫描式取最低 local header，严格式取最高 EOCD），**读出的条目不可控**（实测：2 个文件时读第 1 个，200 个读第 93 个，2000 个读第 991 个）。提示文件无法稳定投递。 |
| xz / zstd | 单向流，同样可用。但 WinRAR 不支持二者；且 zstd 被选作**载荷**格式（见 3.2）。 |

### 3.2 载荷：zstd，不是 gzip

| 方案 | 结论 |
|---|---|
| **zstd** ✅ | Node 22.15+ 原生 `zlib.zstdCompressSync`，零外部依赖。压缩率优于 gzip。每流固定开销 10 字节（gzip 21、xz 68）。 |
| gzip ❌ | 魔数与提示文件相同：载荷流会被按 gzip 扫描的工具直接解出**明文内容**（v0 的实测教训），也让扫描与验证行为更难推理。 |
| xz | 压缩率在大文件极限压缩下优于 zstd（先验：10-30%），但**Node 无原生支持**，需外部二进制或原生编译，打破了"零外部依赖"。每流固定开销 68 字节，对小文件不利。**留作 v2 备选**，届时可按文件大小分流（`src/codec.js` 已按魔数识别，天然支持混用）。 |

### 3.3 提示文件放独立表，不放 `files` 表

放 `files` 表会导致两个问题：

- **`files` 表的约定是"内容是 zstd 流"**，提示文件却是 gzip → 需要给 `files` 加格式标志位，污染 `g` 语义
- **`files` 表的行分布在多个页**，无法保证提示文件独占 page 2

独立表让两者彻底解耦：`notice` 表有自己的格式约定，`files` 表的约定不动。

### 3.4 提示文件同时也是普通归档成员

提示文件**只**在 `notice` 表里的话，它不会出现在还原结果中——用你的工具还原的人看不到它。

解决：`notice` 表里存一份（保证投递），`files` 表里也存一行（作为正常成员，列表可见、还原可见）。两份内容相同、偏移不同，**最低的那个永远赢**，互不干扰。

> 注：当前 v1 实现中 `files` 表固定 zstd，故提示文件**仅**存于 `notice` 表；若要双写，需给 `files` 增加格式标志位。属 v2 事项。

### 3.5 打包后自验证

方案的价值全部押在"自动化流程解出来的是提示文件"这一条上。所以工具必须在产出前**证明**结构保证成立：

> 断言提示文件落在 page 2 内（`[pageSize, 2*pageSize)`）。
> 不满足则拒绝产出、删除产物、退出码非零。

这比"相信设计是对的"可靠——SQLite 的页布局会随行宽、页大小、版本变化。

早期版本还有第二条判据"提示文件之前不存在任何 gzip 流"（逐字节扫描实现）。移除原因：纯 JS 扫描实测约 13MB/s，1GB 归档要约 80 秒，代价随归档规模线性增长；而 page 2 判据单独已构成"任何载荷都不可能更靠前"的充分条件。"扫描器第一个命中的是提示文件"这一端到端性质，后续以另一种方案验证。

**为什么当初也不能断言"全文件恰好一处 gzip 魔数"**：载荷是压缩后的字节，随机撞上 `1f 8b 08` 的概率随载荷体积线性增长（25MB 约 72%）。那种断言会误杀合法归档——实测曾因此把 21MB 的正常包判为失败。此教训对未来的验证方案同样适用。

### 3.6 `--append` 只能追加到本工具的 v1 归档

追加到**旧格式**归档（v0：载荷是 gzip 流、没有 `notice` 表）是不允许的，工具在写入前就会拒绝：

> 旧格式的 gzip 载荷落在 page 2 附近，魔数比新提示文件更靠前 → 提示文件不再是"偏移最低的那个" → 结构保证失效。

与其写完再被自验证拦下（那时数据已提交），不如一开始就拒绝。同理，自验证失败时 `--append` 模式会按 `taskid` 精确删掉刚写入的那一批，恢复到追加前的状态。

### 3.7 载荷算法与容器结构解耦

`src/codec.js` 按魔数自动识别内容格式（gzip / zstd / zip），`src/load.js` 不关心某个文件当初是用什么算法压的。因此：

- 换载荷算法 = 改 `src/save.js` 里一个常量
- 未来按文件大小分流（大文件 xz、小文件 zstd）= 零格式改动
- 读取端天然兼容历史归档

### 3.8 同名产物不覆盖，自动改名

非 `--append` 模式下若产物路径已有文件，POC 阶段的实现是**先删后写** —— 隐患在于：新打包一旦失败（源含目录符号链接、磁盘满、自验证不通过），旧归档已被销毁且不可恢复；"不留半成品"只保护了新产物，没保护既有产物。

现在改为仿 Windows 资源管理器的自动改名：`test.zip` → `test (2).zip` → `test (3).zip`……不覆盖、不删除任何已有文件。代价是产物名不再确定（连续打包会得到一串文件），换来既有数据在任何失败路径下都完好。更复杂的冲突策略（提示、`--force` 覆盖等）留待后续。

### 3.9 文件头伪装：默认开启（2026-11-20 起；`--honest` 显式退出）

头部嗅探类工具（libmagic / `file`）看文件头魔数。产物默认把前 16 字节用 zip local header 前缀**原位覆盖**（SQLite 魔数是纯魔数，零信息量、可无损还原），让这类工具改判 zip —— 头部是格式识别链条的第一环，默认就该是伪装的。

> 历史决策：本项最初为可选（`--disguise`，2026-10-24 引入，默认诚实头），当时的理由是"诚实头让任意 SQLite 客户端可直接打开、自身工具链零额外步骤，伪装是有代价的策略选择"。2026-11-20 反转为默认开启：产品的核心主张就是"被识别为压缩包"，头部曾是最大的暴露面，把伪装做成默认、把诚实头降为显式选项（`--honest`）更符合目标 1/2。原取舍中仍然成立的部分——SQLite 客户端拒开 `SQLITE_NOTADB`、`load` 走临时副本的开销——如今是**所有默认产物的代价**（见 KNOWN_ISSUES 第 23 条），`--honest` 是唯一完全回避方式。

约束与取舍（反转后仍适用）：

- **只能动 16 字节**：偏移 16 起是 page size、`user_version` 等真实字段；完整 local header（30 字节）放不下，16 字节对"识别级"判断已够用。
- **绝不写外来文件**：还原/追加前先做结构预检（PK 前缀 + 偏移 60 == 1 + 合法页大小），预检不过不碰文件一个字节；预检过了但验证失败，也把原字节原样写回。
- **load 只读**：伪装头归档复制到临时文件还原后打开，原文件不动（避开并发打开与崩溃窗口的边界问题）。
- **append 状态保持**：追加目标无论原本是伪装头还是诚实头，追加后都按**其原有状态**恢复；旗标不参与追加（`--append` 时 `--honest` / `--disguise` 均不影响结果）。追加不会静默改变归档的伪装状态。
- **不追加 EOCD**：想让严格 zip 解析器（Python `zipfile` / libarchive）接受就必须构造合法 zip 结构，那是 §4 已否决的"双格式"路线。文件头伪装只解决头部嗅探这一层。
- **`--disguise` 兼容保留**：已是默认行为，接受但无效果（与 `--honest` 互斥报错），避免旧脚本报"未知选项"。

## 4. 已知权衡（未消除）

| 权衡 | 说明 |
|---|---|
| **严格解析器判非法** | Python `zipfile` / libarchive / .NET 全部拒绝。要让它们接受，文件本身必须是合法 zip（"双格式"路线），而那条路线会让扫描器解出诱饵 zip 里的条目，暴露面更大。**"看起来是 zip"与"能被严格库接受"在结构上互斥。** |
| **7-Zip 跟随扩展名** | 字节相同的文件，命名 `.zip` 时 7-Zip 强制用 zip 解析器（要求 EOCD 在末尾）→ 失败 → 回退启发式扫描 → 可能误判；命名 `.db` 等则正确识别。WinRAR / Python / libarchive 不受影响。 |
| **提示文本是明文** | gzip 不是加密，拿到文件的人用 `zlib.gunzipSync` 就能读出提示文本。**这是有意的**——提示文本本来就是要给人看的。 |
| **载荷可被专门工具解出** | zstd 不是加密，懂行的人能从 db 里还原全部内容。**这是有意的**——本方案解决的是"格式识别"与"自动化流程审查"，不是保密。 |

## 5. v1 范围

**做**：

- 目录 / 单文件 → 单个 SQLite 数据库文件（默认 `.zip`）
- 载荷 zstd、提示 gzip、提示文件独占 page 2
- 打包后自验证（page 2 结构验证；不通过则拒绝产出）
- 还原全部批次
- 统一的错误处理：任何失败 → 一行人话 + 退出码 1，**不产生半成品**
- `PRAGMA user_version` 记格式版本

**不做**（v2 候选）：

- 加密 / 密码保护
- 按文件大小分流 xz / zstd
- 提示文件双写（`files` 表也存一份）
- 按 `taskid` 选择批次还原
- 还原路径越界校验
- 测试套件 / lint / CI / git 仓库（测试套件已于 2026-10-31 落地：根目录 `npm test` 聚合 CLI / GUI / 互通 / selftest 四套件；lint / CI / git 仍无）

## 6. 错误处理约定

| 约定 | 说明 |
|---|---|
| 统一出口 | 所有失败走 `fail()`：只打一行人话 + 退出码 1，**不打堆栈** |
| 不留半成品 | 非 `--append` 模式下失败即删除产物 |
| 不提交部分数据 | 写入出错则 `ROLLBACK`，绝不 `COMMIT` 半截数据 |
| 逐条容错 | 还原时单个条目失败不中断整体，但计数并在最后以非零退出码收场 |
| 参数严格 | 未知选项、缺值、多余位置参数一律报错退出，不静默忽略 |
| 错误可定位 | 每条错误带上是哪个文件/哪一步失败 |
