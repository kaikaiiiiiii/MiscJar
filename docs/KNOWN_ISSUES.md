## 问题清单

### 1. `load` 不按批次过滤，把所有批次一并还原

- **级别**：高
- **位置**：`src/load.js:114`（`SELECT rpath, g, content FROM files`，无 WHERE 子句）
- **现象**：同一个归档里若存在多个 `taskid`，还原时会全部读出。同一条 `rpath` 被多个批次覆盖时，以 `id` 更大（后写入）的为准。
- **触发条件**：对同一个归档 `--append` 两次以上（多批次共存时）。
- **根因**：写入侧用 `taskid` 标记批次，但读取侧完全没有批次概念，`src/load.js` 中不存在任何按 `taskid` 过滤或选择批次的代码路径。
- **证据**：代码推导（`src/save.js:260`、`src/save.js:270` 写入 `taskid`，`src/load.js:114` 无条件全表扫描）。

### 2. 打包单个文件时目录结构丢失

- **级别**：高
- **位置**：`src/save.js:313`（`root = path.dirname(source)`）
- **现象**：打包目录时顶层目录名会保留（`test/hello.txt`）；打包单个文件时 `root` 变成该文件的父目录，`rpath` 只剩文件名。往返后文件落在还原根目录，不再位于原来的子目录中。
- **触发条件**：执行 `node src/save.js /path/to/some/file.txt`。
- **根因**：`root` 的定义对「目录」和「文件」两种输入不等价 —— 对目录而言 `dirname` 恰好是归档根，对文件而言 `dirname` 是文件所在目录。
- **证据**：代码推导。目录情形实测 `rpath = test\hello.txt`；文件情形按同一公式推得 `rpath = hello.txt`。

### 3. 路径不存在时抛出无信息量的 `TypeError`

- **级别**：高
- **位置**（旧版）：`pathCheck` 无 `else` 分支 + `main` 未检查返回值
- **现象**：路径拼错时抛出 `TypeError [ERR_INVALID_ARG_TYPE]`，报错指向 `path.dirname(undefined)`，完全看不出真正原因是「路径不存在」。
- **根因**：`pathCheck` 只在两条成功分支里 `return`，其余情况隐式返回 `undefined`。
- **证据**：代码推导。
- **现状**：**已消除**。`pathCheck` 在不匹配任何分支时返回原值（`src/save.js:54`），`main` 亦有存在性前置检查（`src/save.js:308`）；路径不存在时输出「错误: 路径不存在: <路径>」并以退出码 1 结束。

### 4. `pathCheck` 的引号正则覆盖面极窄

- **级别**：低（原判中 —— 旧版会落入第 3 条的崩溃路径，当前失败受控，只剩报错不够直接）

- **现象**：只识别「单字母盘符 + 反斜杠 + 结尾双引号」这一种形态。POSIX 路径、带正斜杠的 Windows 路径（`C:/x/y"`）、非结尾引号一律不匹配 —— 此时引号不会被剥掉，路径按原样参与存在性检查，最终报「路径不存在」（错误信息里可见残留引号）。
- **触发条件**：在 PowerShell 里粘贴带引号的非 Windows 风格路径。
- **根因**：正则按单一平台的单一写法硬编码，未做引号剥离的通用处理。
- **证据**：代码推导（`src/save.js:35-43`）。

### 7. `src/load.js` 未调用 `db.close()`

- **级别**：中

- **现象**：脚本没有显式的数据库资源生命周期，靠事件循环排空后自然退出。

### 8. 全流程同步 I/O，阻塞事件循环

- **级别**：中
- **位置**：`src/save.js:137`（`readdirSync`）、`src/save.js:149`（`lstatSync`）、`src/save.js:265`（`readFileSync` + 同步压缩）；`src/load.js` 侧写盘同为同步（`src/load.js:54-58`）
- **现象**：整个打包流程是同步的，无法与其他异步任务并发；目录项越多、文件越大，耗时越明显。
- **触发条件**：打包大目录树或大文件。
- **根因**：所有 I/O 都用了 `*Sync` 变体（zstd 压缩亦为同步 `zstdCompressSync`）。
- **证据**：代码推导。内存占用按单文件计，不会随目录总量线性增长。

### 9. 单个超大文件整体读入内存后才压缩

- **级别**：中
- **位置**：`src/save.js:265`
- **现象**：文件内容先被完整读进内存（Buffer），再整体 zstd 压缩。单个超大文件的峰值内存占用 ≈ 文件原始大小 + 压缩后大小。
- **触发条件**：打包超大文件。
- **根因**：使用了 `fs.readFileSync` + `codec.FORMATS.zstd.encode`（内部 `zlib.zstdCompressSync`）这一对非流式 API。
- **证据**：代码推导。

### 10. 目录符号链接导致打包失败

- **级别**：中（原判高 —— 旧版为未捕获崩溃且可能残留空库；当前为受控失败，按级别定义降为中）
- **位置**：`src/save.js:149`（`lstatSync` 判定）、`src/save.js:264-268`（`readFileSync` 与错误捕获）
- **现象**：源目录中若含**指向目录的符号链接**（Windows 上的 junction 亦然），打包整体失败：该链接被判为普通文件（`g = 0`），`readFileSync` 报 `EISDIR`；错误被收集后整个事务 `ROLLBACK`、产物删除，输出「错误: 读取或压缩失败 <路径>: EISDIR …」并以退出码 1 结束，不留半成品。
- **触发条件**：源目录包含目录符号链接 / junction。在 macOS、Linux 上很常见（开发目录、`node_modules` 里的链接）。
- **根因**：`lstatSync` **不跟随**符号链接，对目录符号链接返回 `isDirectory() === false`，于是被判为普通文件（`g = 0`）；随后 `fs.readFileSync` 对目录读取失败。
- **证据**：实测（Node v24.22.0 / Windows，junction 指向目录）：报错「错误: 读取或压缩失败 <路径>: EISDIR: illegal operation on a directory, read」，退出码 1，产物未生成。旧版中该异常发生在 `forEach` 回调内且无 try/catch，直接冒泡终止进程并可能残留 0 行空库 —— 崩溃模式已消除，「含目录符号链接的目录无法打包」本身未消除。

### 11. 符号链接被展开为普通文件，且不保留任何文件元数据

- **级别**：中
- **位置**：`src/save.js:149`（`lstatSync` 的用法）、`src/save.js:265`、表结构 `src/save.js:240-247`
- **现象**：**指向文件的**符号链接，其链接目标内容被读取入库，还原后变成一个内容相同的**普通文件**，链接关系丢失。权限位、mtime、硬链接同样不记录。
- **触发条件**：源目录中包含文件符号链接，或用户依赖 mtime / 权限位。
- **根因**：`lstatSync` 的结果只被用来区分「目录 / 非目录」两种情况，符号链接与普通文件不作区分；表结构中也没有任何对应列。
- **证据**：代码推导 + 实测表结构确认无对应列。

### 12. 没有完整性校验

- **级别**：中
- **位置**：表结构 `src/save.js:240-247`；解压处 `src/load.js:139`
- **现象**：表中没有 size / checksum 列。BLOB 若损坏，检测能力完全取决于压缩格式自身：gzip 流（提示文件、历史 v0 载荷）自带 CRC32，损坏在解压时报 `Z_DATA_ERROR`（实测翻转压缩字节即报错）；zstd 帧（v1 载荷）默认**未开启**内容校验和（帧头 checksum 位为 0，实测 Node v24.22.0），翻转压缩块中的字节后解压**不报错**、解出的内容与原文**不一致** —— 载荷损坏可能完全静默。解压失败按条目捕获并带文件名输出（「还原失败 <rpath>: …」，`src/load.js:120-123`），单个条目失败不中断整体 —— 报错可定位，但格式层面没有完整性字段兜底。
- **触发条件**：归档文件在传输或存储过程中损坏。
- **根因**：格式本身未设计校验字段（见 `DATA_FORMAT.md`）；Node 的 `zstdCompressSync` 默认不写内容校验和。
- **证据**：代码推导 + 实测（Node v24.22.0：zstd 帧头 checksum 位为 0，翻转压缩字节后 `zstdDecompressSync` 正常返回且结果与原文不等；gzip 同样翻转报 `Z_DATA_ERROR`）。

### 22. 覆盖模式先删除旧产物，打包失败则旧归档丢失

- **级别**：高
- **位置**（旧版行为）：非 `--append` 且产物已存在时，先 `unlinkSync` 已有产物再开始打包
- **现象**：非追加模式下，若产物路径已有归档，旧归档会**先被删除**；随后新打包失败（源含目录符号链接、磁盘满、自验证不通过等）时，旧归档已不可恢复 —— 「不留半成品」约定只保护了本次新产物，未保护既有产物。
- **触发条件**：对已有归档的同名路径再次打包且中途失败。
- **根因**：POC 阶段的妥协 —— 为保证「默认得到全新归档」而先删后写。
- **证据**：代码推导（旧版覆盖分支在打包前 `unlinkSync` 产物）。
- **现状**：**已消除**（2026-10-24）。默认不再覆盖：同名产物自动改名（`test.zip` → `test (2).zip` → `test (3).zip`…，仿 Windows 资源管理器；`src/save.js:58-67` `nextAvailablePath`、`src/save.js:336-340`），失败也只影响本次新产物。实测含目录链接的源打包失败后旧归档完好、无半成品残留。

### 23. 默认伪装头的固有代价

- **级别**：低
- **位置**：`src/save.js` 伪装流程（`writeHeader` / `looksDisguised` / `revealArchive`，`src/save.js:70-101`）、`src/load.js` 临时副本（`src/load.js:76-94`）
- **现象**：(a) 默认产物（PK 伪装头）无法用 SQLite 客户端直接打开（报 `SQLITE_NOTADB`）；(b) `src/load.js` 打开伪装归档需整份复制到临时文件、还原魔数后再读 —— 大归档有相应的时间与磁盘开销；(c) `--append` 需先还原魔数、结束后按原状态恢复（失败回滚路径同样恢复）。
- **触发条件**：使用默认文件头打包的归档（2026-11-20 起为全部默认产物）。
- **根因**：伪装头与 SQLite 自身的魔数校验互斥，属设计选择而非缺陷（2026-11-20 起默认开启，见 `DESIGN.md` 3.9）。
- **证据**：实测（Node v24.22.0：伪装头产物以 SQLite 打开报 `SQLITE_NOTADB`；`load` 后原文件字节不变、临时副本无残留；append 失败回滚后伪装头恢复）。
- **现状**：**固有**（默认行为的代价；`--honest` 是唯一完全回避方式 —— 产物保留诚实 SQLite 头，行为与 2026-10-24 至 2026-11-19 期间的默认完全一致）。

## 第二版实测发现（格式重构期间）

以下问题是在 v1 格式（载荷 zstd + 提示 gzip）实测中暴露的，**部分已在重构中消除**，此处记录以便追溯。

### 17. 严格按格式解析的解压库直接判非法

- **级别**：高
- **位置**：格式层面（与具体实现无关）
- **现象**：Python `zipfile` 报 `BadZipFile: File is not a zip file`；libarchive 报 `Unrecognized archive format`；.NET `System.IO.Compression` 打开成功但 **0 个条目**。只有 WinRAR、7-Zip 这类会**扫描文件头**的实现能读出内容。
- **触发条件**：任何一次解压。
- **根因**：产物是 SQLite 数据库，不含 zip 的 EOCD/中央目录；严格实现找不到这些结构即判非法。扫描型实现则靠魔数匹配。
- **证据**：实测。5 种解压实现 × 4 种内容格式的完整对照。
- **现状**：**未消除**，且是格式的固有属性。要让严格库也接受，就必须让文件本身是合法 zip（"双格式"路线）。

### 18. 7-Zip 跟随扩展名，行为与文件内容不一致

- **级别**：中
- **位置**：外部工具行为（非本项目代码）
- **现象**：**字节完全相同**的同一个文件，命名为 `.zip` 时 7-Zip 报 `Cannot open the file as [zip] archive` 并误判为 lzma、吐出垃圾；命名为 `.db`/`.bin`/`.txt`/无扩展名时则正确识别为 zip 并解出内容。WinRAR、Python、libarchive 不受影响。
- **触发条件**：产物命名为 `.zip`（本项目的默认行为）。
- **根因**：7-Zip 见到 `.zip` 扩展名就固定使用 zip 解析器的"按 zip 打开"模式（要求 EOCD 位于文件末尾），失败后回退到启发式扫描，容易误命中 lzma。
- **证据**：实测 5 种扩展名 × 5 种解压实现。

### 19. zip 作为内容格式时，读出的条目不可控

- **级别**：高
- **位置**：格式层面（实验期方案，已弃用）
- **现象**：若每个文件的内容存为一个完整 zip 条目，读取端**读出的条目随文件规模漂移**：2 个文件时读到第 1 个，200 个时读到第 93 个，2000 个时读到第 991 个。提示文件无法稳定投递。
- **触发条件**：使用 zip 条目作为内容格式。
- **根因**：zip 是随机访问格式，嵌入后中央目录记录的绝对偏移全部失效，需 `concat = EOCD位置 - cd_size - 记录的cd_offset` 补偿；而不同实现的补偿与选取规则不一致 —— 扫描式取**最低**偏移的 local header，严格式取**最高**偏移的 EOCD。两种规则互斥，无法用一个位置同时满足。
- **证据**：实测（偏移表 + 各实现读出的条目名）。
- **现状**：**已消除** —— 改用 gzip / zstd 等单向流格式，选取规则统一为"偏移最低者胜"。

### 20. gzip 魔数导致内容明文泄漏

- **级别**：中
- **位置**：历史格式（v0，`zlib.gzipSync` 存载荷）
- **现象**：v0 格式把每个文件的内容以 gzip 流存入 BLOB，因此文件里存在 N+1 处 `1f 8b 08` 魔数。任何按 gzip 扫描的工具解出来的都是**某个归档文件的明文内容**（不是文件名，是内容本身），且泄漏哪一个取决于 SQLite 的物理页布局，不受控制。
- **触发条件**：使用 v0 格式打包。
- **根因**：gzip 容器头固定在流开头，压缩即等于在文件里留下可被扫描的标记。
- **证据**：实测（6 个文件的 gzip 魔数偏移呈完美逆序：7828→F6、7894→F5 … 8158→F1）。
- **现状**：**已消除** —— v1 载荷改用 zstd（`28 b5 2f fd`），gzip 魔数在提示文件之前不存在。

### 21. SQLite 页布局决定哪个流会被扫描到

- **级别**：中
- **位置**：`src/save.js` 建表顺序、`verifyNotice()`
- **现象**：同一页内，**后插入**的 cell 物理偏移更小。因此"最后写入的那一行"恰好是偏移最低的流，也正是扫描器会命中的那个。一旦归档大到跨越多页，规则变为"**第一个叶页里最后写入的那一行**"——页满后新行进到更高偏移的新页，最后写入的行反而被甩到最末尾。
- **触发条件**：归档规模跨页（旧格式实测断点在 73 个文件左右）。
- **根因**：SQLite 的 B-tree 页分配规则。
- **证据**：实测（n=6/20/50/73/80/100/300 逐档对照）。
- **现状**：**已缓解** —— 提示文件放进最先创建的独立表（独占 page 2），其偏移必然低于所有载荷，与规模无关；`src/save.js` 另有自验证兜底。
